# 추적성 매트릭스

- `trace.csv`: 요구사항(SWR) 하나가 한 행이다. 요구사항 -> 컴포넌트 -> 모듈 -> 단위/통합/시스템 시험을 양방향으로 연결한다.
- `oem_trace.csv`: OEM 요구/인터페이스(OEM-*)가 어떤 SWR로 도출되었는지 연결한다. `trace.csv`의 `source` 열과 양방향으로 일치해야 한다.
- 검사: `ci/in-docker.sh python3 ci/check_traceability.py`

## 열 규칙
- `status`: `planned`(연결 예약) / `implemented` / `verified`. `planned`는 컴포넌트와 시험 ID가 예약되어 있어야 하고, 시험 ID의 실재 확인은 `implemented` 이상에서 한다.
- `source`는 `OEM-*` 또는 가정 ID(`A-nn`)만 쓴다. 가정은 `docs/requirements/assumptions.md`에 있어야 한다. 요구사항 문서의 출처 열과 같은 집합이어야 한다.
- 요구사항 문서의 `검증` 열에 `단위`가 있으면 `unit_tests`, `통합`이 있으면 `integration_tests`, `시스템`이 있으면 `system_tests`가 연결되어야 한다.
- 시험은 소스의 `@test <ID>`와 `@requirement <SWR ID>` Doxygen 태그로 연결한다.
- 시스템 시험 요구사항 커버리지: 기능/품질 요구사항의 100%가 시스템 시험에 연결되어야 한다.
- 우선순위는 이터레이션 1의 모든 요구가 OEM 입력 또는 안전 요구의 구현에 필요하므로 `필수`다.
- 제약사항(SWR-109, 110, 112, 115, 116, 117)은 시험 대신 빌드, 정적 분석, 리뷰로 검증하며 모든 컴포넌트에 적용된다.

## 컴포넌트 ID (초안, 아키텍처 단계에서 확정)

| ID | 이름 | 초안 책임 |
|---|---|---|
| C-VAL | 입력 검증기 (InputValidator) | 입력 정규화, 형식·범위 검증, freshness 판정 |
| C-ARB | 판정기 (Arbiter) | 우선순위 규칙 평가, 출력 결정, 충돌 래치 |
| C-STA | 상태 관리기 (StateManager) | 상태(NORMAL/DEGRADED/FAULT/OFF), 경고코드, 초기 상태 |
| C-CTL | 제어기 (Controller) | 평가 진입점, 결과 조립, 이유코드 매핑 |
