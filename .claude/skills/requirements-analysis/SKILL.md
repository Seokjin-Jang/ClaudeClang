# 요구사항 분석 (A-SPICE SWE.1)

## 분류 체계

| 구분 | 하위 구분 | 비고 |
|---|---|---|
| 기능 요구사항 | 일반 기능 | 시스템이 "무엇을 하는가" |
| | 기능 안전 요구사항 | **별도 문서에서 관리**한다. 이 문서에는 작성하지 않고 참조 ID만 둔다. |
| 비기능 요구사항 | 품질 | **ISO 25010** 품질 특성 기준 |
| | 제한 (Limitation) | 자원, 성능 한계 등 수치로 표현 가능한 상한/하한 |
| | 제약사항 (Constraint) | 표준, 언어, 도구, 플랫폼, 법규 등 설계 선택지를 제한하는 조건 |

### 품질 요구사항 (ISO 25010)
각 품질 요구사항은 아래 특성 중 하나에 반드시 매핑한다.
기능 적합성 / 성능 효율성 / 호환성 / 사용성 / 신뢰성 / 보안성 / 유지보수성 / 이식성
(필요 시 하위 특성까지 명시: 예 `신뢰성 > 성숙성`)

## 작성 규칙
- 요구사항 하나에는 하나의 내용만 담는다. (원자성)
- "shall" 형태의 검증 가능한 문장으로 쓴다. 모호한 표현("적절히", "빠르게", "등")은 금지하고 수치와 조건을 쓴다.
- 구현 방법이 아니라 외부에서 관찰 가능한 동작을 기술한다.
- 모든 요구사항에 고유 ID, 우선순위, 검증 방법(시험/분석/검사/시연), 출처를 부여한다.

## 양방향 추적성 (필수)
모든 요구사항은 이후 산출물과 **양방향**으로 연결한다.

```
상위 요구사항(시스템) <-> SW 요구사항 <-> 아키텍처 컴포넌트 <-> 상세 설계 모듈
                                     <-> 통합 테스트 <-> 단위 테스트 <-> 소스 코드
```

- 순방향: 요구사항 -> 설계/구현/테스트 어디에도 연결되지 않은 요구사항이 없어야 한다.
- 역방향: 설계/코드/테스트 -> 근거 요구사항이 없는 항목이 없어야 한다. (불필요 기능 방지)
- 추적성 매트릭스를 산출물에 포함하고, 변경 시 영향 분석을 수행한다.

## 산출물
1. 소프트웨어 요구사항 명세서 (기능 / 비기능 구분)
2. 추적성 매트릭스
3. 완료 후 `review` 스킬로 요구사항 체크리스트 리뷰
